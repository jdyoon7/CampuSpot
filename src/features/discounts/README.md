# 할인·혜택 제보와 검수

할인·혜택 메뉴(`/discounts`)에서 로그인한 사용자가 매장명, 할인 내용·조건, 날짜 범위 또는 상시 여부, 공식 공지 링크를 제출합니다. 제출 직후와 새로고침 후 모두 **내 제보**에서 검수 상태를 확인할 수 있습니다. 접수한 자료의 공식 출처 여부는 검수자가 판단합니다.

| 원본 요구                         | 구현                                                               | 확인 방법                                              |
| --------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------ |
| 6-5 신규 제보, 공식 SNS·공지 링크 | `DiscountsPage.tsx`, `components/ReportForm.tsx`, `api/reports.ts` | `npm run test:account` 안의 discounts-reports 시나리오 |
| 6-2 기간·검수 상태와 본인 조회    | `components/MyReports.tsx`, discount_reports migration             | 제출 직후 pending. 내역은 최신순 20건씩 조회           |
| 6-5 중복 및 권한                  | DB 제약, RLS, 컬럼별 INSERT 권한                                   | `npm run db:test` 안의 discounts_reports.test.sql      |
| 제보 포인트 보상                  | 후속 작업                                                          | 별도 단계에서 연결합니다.                              |

공통 인증 migration 다음에 `supabase/migrations/20261123073314_discounts_create_reports.sql`을 적용합니다. 테이블은 사용자 FK로 `profiles(id)`를 참조합니다. 접수 상태와 시각은 DB가 지정하고, 회원은 본인 명의 등록·본인 조회가 가능합니다. 동일 작성자의 매장명·할인 내용·출처·기간이 같은 검수 대기 제보는 중복 저장되지 않습니다. 가입 계정 삭제 시 해당 제보도 삭제됩니다.

로컬 Supabase와 공개 키를 준비하는 순서는 [계정 개발 안내](../auth/README.md)에 있습니다. 기존 개발 DB에서는 `npx supabase migration up --local` 후 앱을 시작하세요. 혜택 제보는 추가 API 키가 필요하지 않습니다. `npm run check`, `npm run db:test`, `npm run test:account`가 각각 입력 검증, DB 권한, 실제 등록 화면을 검사합니다. 기능을 되돌릴 경우 UI 커밋을 revert하고 공유 DB에 접수된 제보는 보존합니다.

## 증빙 사진과 혜택 지도

**혜택 제보하기**에서 JPG·PNG 한 장을 선택할 수 있습니다. 사진은 브라우저에서 긴 변을 최대 1,200px로 줄인 뒤 PNG로 전송합니다. 서버가 파일을 다시 디코딩해 최대 2MB의 PNG로 저장하고 제보를 등록합니다. 등록에 실패하면 결과를 확인한 뒤 업로드를 정리합니다. 이미 접수된 제보의 사진은 **내 제보**에서 열 수 있습니다. 검수 담당자는 검수 대기 상태의 사진을 볼 수 있습니다.

`20261127031600_discounts_map_and_evidence.sql`이 비공개 `discount-evidence` 버킷과 읽기 정책을 추가합니다. 공개 혜택에서는 증빙 자료를 조회하지 않습니다. 새 환경에는 마이그레이션을 먼저 적용하고 `discount-evidence` 함수와 탈퇴 시 사진을 정리하는 `core-account` 변경을 함께 반영합니다. 로컬 Supabase에서 검증할 때는 `supabase functions serve`로 두 함수를 실행합니다.

**할인·혜택 → 혜택 지도**는 공개 중인 혜택이 연결된 지점만 20곳씩 표시합니다. `.env.local`의 `VITE_KAKAO_MAP_APP_KEY`에는 카카오 JavaScript 키를 넣고 해당 키에 앱 도메인을 등록합니다. 키가 없거나 매장 위치를 찾지 못한 경우에도 목록의 주소와 외부 카카오맵 링크를 이용할 수 있습니다. [카카오 지도 Web API 가이드](https://apis.map.kakao.com/web/guide/)

공유 개발 DB에 마이그레이션을 적용했습니다. `npm run check`, 모바일 E2E 4개, 롤백 SQL 검사 10개와 Deno 타입 검사를 통과했습니다. 로컬 함수를 개발용 Auth·Storage에 연결해 사진 등록, 작성자·검수자 열람, 비인가 차단을 확인했습니다. 지도 핀은 SDK 모의 응답으로 검증했습니다. 공유 개발 프로젝트의 함수 배포와 실 카카오 JavaScript 키 연결은 별도 설정입니다.

## 관리자 검수

관리자 또는 최고 관리자 계정으로 로그인한 뒤 **할인·혜택 → 제보 검수하기**(`/discounts/review`)를 엽니다. 공식 공지를 확인하고 **승인** 또는 **반려 → 사유 입력 → 반려 확정**으로 처리합니다. 대기 목록은 자신의 제보를 제외하고 오래된 순서로 20건씩 표시합니다. 승인된 혜택은 비로그인 방문자도 볼 수 있고, 종료일이 지난 혜택은 한국 날짜 기준으로 공개 목록에서 제외합니다. 반려 결과와 사유는 작성자의 ‘내 제보’에서 확인합니다.

개발 PC에서 테스트하려면 로컬 Supabase에 제보용·검수용 두 계정을 만들고, 로컬 Studio의 Table Editor → user_roles에 **검수용 계정의 UID**와 role `admin`으로 한 행을 추가합니다. 기존 member 행은 유지하세요. 등록 직후 검수 계정에서 페이지를 새로고침합니다. 같은 절차를 자동으로 실행하는 테스트는 `npm run test:account`에 포함되어 있습니다.

| DB 계약                                                      | 동작                                                                                                                                                          |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `review_discount_report(p_report_id, p_decision, p_reason?)` | 서버가 admin/super_admin, 작성자와 검수자의 분리, pending 상태를 확인합니다. approved는 사유 없이, rejected는 공백을 제외한 1~500자 사유로 처리합니다.        |
| `list_published_discounts(p_limit, p_offset)`                | 승인된 기간 미종료·상시 혜택의 매장, 내용, 공식 출처, 기간과 검수 시각을 돌려줍니다. 검수 전 원본과 반려 사유는 비공개입니다.                                 |
| `core_private.discount_review_log`                           | 상태 변경과 같은 트랜잭션에 제보 ID, 검수자, 결정, 시각을 한 번 기록합니다. 감사 기록은 제보 삭제 후에도 보존하며 검수자 탈퇴 시 해당 사용자 참조를 비웁니다. |

제보 등록 migration 다음에 `20261123094548_discounts_review_reports.sql`을 적용합니다. 두 관리자가 같은 건을 처리하면 먼저 저장된 결정이 유지됩니다. 운영 DB 적용 전 백업을 확인하고, 기능 철회 시 RPC 실행 권한과 대기 목록 정책을 먼저 회수한 뒤 화면 변경을 되돌립니다. 이미 접수한 제보와 감사 기록은 보존합니다.

## 공개 혜택 검색

할인·혜택 메뉴에서 매장명이나 할인 내용의 일부를 입력하고 **검색**을 누릅니다. **초기화**하면 조건을 지우고 전체 목록 첫 페이지로 돌아갑니다. 비회원도 사용할 수 있습니다.

- **오늘 이용 가능**은 한국 날짜 기준으로 시작일과 종료일 사이에 있거나 상시인 혜택입니다. 학생증 제시 등 세부 이용 조건은 공지에서 확인합니다.
- **마감 임박**은 오늘부터 6일 뒤까지(총 7일) 종료되는 혜택입니다. 두 조건을 함께 선택하면 오늘 이용 기간에 들어온 마감 임박 혜택만 표시합니다.
- 검색 RPC `search_published_discounts`는 승인된 미종료 혜택의 매장명·설명에서 대소문자와 띄어쓰기를 무시하고 부분 일치로 조회합니다. 검색과 날짜 조건을 먼저 적용한 뒤 페이지를 나눕니다. 기존 공개 목록 RPC도 같은 공개 조건을 사용합니다.
- 인근 학교·지역·업종 필터는 공개 혜택과 연결된 지점의 검색 분류를 사용합니다. 선택지를 조합한 뒤 **검색**을 누르면 모든 조건에 맞는 혜택이 표시됩니다. 인근 학교는 매장 위치 기준이며 이용 자격은 혜택 설명에서 확인합니다. 분류가 없는 혜택은 전체 검색에서 조회할 수 있습니다.

공개 검색 화면은 `search_discount_catalog`를 사용합니다. `20261126081235_discounts_catalog_filters.sql`을 공유 개발 DB에 적용했고 기존 고려대 식당 3곳을 **고려대학교 / 서울 성북구 / 음식점·식당**으로 분류했습니다.

제보 검수 migration 다음에 `20261123095813_discounts_search_published.sql`을 적용합니다. `npm run db:test`에서 공개 범위와 날짜 경계를, `npm run test:account`에서 비회원 검색 흐름을 검사합니다.

## 혜택 캘린더

**할인·혜택 → 혜택 캘린더**(`/discounts/calendar`)에서 비회원도 오늘부터 날짜별 혜택을 볼 수 있습니다. 서울 시간 기준 오늘이 기본 선택이며, 날짜를 바꾸면 목록 첫 페이지로 돌아갑니다. 시작일과 종료일 당일을 포함하고 상시 혜택은 모든 선택 가능 날짜에서 표시합니다. 종료되었거나 아직 승인되지 않은 제보는 공개하지 않습니다.

`list_discount_calendar(p_day, p_limit, p_offset)`는 공개 혜택 필드만 최신 검수순으로 반환합니다. 목록은 20개씩 표시합니다. 공유 개발 DB에 `20261125071251_discounts_calendar.sql`을 적용했습니다. 확인 결과는 `npm run check`와 `npm run test:e2e` 통과, 공유 개발 DB에서 롤백 방식으로 날짜 및 공개 권한 SQL 검증 5개 통과, 모바일 브라우저에서 날짜 이동과 오늘 복귀 통과입니다. 로컬 Docker DB 테스트 전체 실행은 Docker CLI가 없어 수행하지 않았습니다.

캘린더 노출을 되돌릴 때는 화면 변경을 되돌립니다. 추가한 조회 함수는 데이터에 쓰지 않습니다.

## 공개 혜택 정정 제보

공개 목록이나 캘린더에서 **수정·종료·오류 제보**를 열어 사유를 입력합니다. 내용 수정 유형은 공개할 새 할인 내용도 받습니다. 로그인 회원은 혜택당 검수 대기 제보를 한 건씩 접수할 수 있습니다. **내 정정 제보**에서 상태와 반려 사유를 확인할 수 있습니다.

관리자는 **제보 검수하기 → 정정 제보 검수 대기**에서 접수 당시 내용, 수정 제안, 사유와 공식 공지를 확인합니다. 내용 수정 승인 시 공개 설명을 교체하고, 종료·오류 승인 시 검색과 캘린더에서 혜택을 내립니다. 승인 전에 혜택이 변경되거나 종료된 경우 검수자는 현재 상태를 확인하고 해당 제보를 반려할 수 있습니다. 반려 후에는 기존 공개 상태가 유지됩니다.

캘린더 migration 다음에 `20261126030644_discounts_corrections.sql`과 `20261126031240_discounts_correction_visibility.sql`을 순서대로 적용합니다. 인증된 요청의 작성자와 권한은 RPC가 확인하며 직접 쓰기는 서버 전용입니다. 작성자는 자기 제보를, 관리자는 대기 건을 읽을 수 있습니다. 검수자 식별자는 API 조회에서 제외됩니다.

공유 개발 DB에서 롤백 방식 SQL 검증과 모바일 브라우저 정정 접수·수정 승인·종료 승인·오류 반려를 확인했습니다. `npm run check`, `npm run test:e2e`를 통과했습니다. 로컬 Docker DB 전체 테스트는 Docker CLI가 없어 실행하지 않았습니다. 기능 철회가 필요하면 정정 화면과 RPC 실행 권한을 회수하고, 검수 기록 및 공개 중단 상태는 유지합니다.

## 혜택 저장

로그인한 회원은 공개 검색 결과나 캘린더에서 **혜택 저장**을 누르고 **할인·혜택 → 저장한 혜택**(`/discounts/saved`)에서 기록을 확인할 수 있습니다. 완료된 혜택이나 공개를 중단한 혜택은 제목과 상태로만 표시되며, 저장 목록에서 해제할 수 있습니다. 동일한 매장명이 생겨도 혜택 ID 단위로 저장하기 때문에 서로 섞이지 않습니다. 매장과 지점을 구분하는 데이터는 이후 매장 기능에서 연결합니다.

정정 제보 migration 다음에 `20261126064652_discounts_offer_bookmarks.sql`을 적용합니다. `set_discount_offer_bookmark`는 현재 로그인한 사용자의 저장 상태를 변경하고, 공개 중인 혜택만 저장합니다. 사용자와 혜택의 조합이 고유하므로 같은 요청을 다시 받아도 한 번만 저장됩니다. 저장 목록은 `list_my_discount_offer_bookmarks`에서 20개씩 조회합니다.

공유 개발 DB에 적용했고, 롤백 방식의 SQL 검사 14개와 모바일 브라우저의 저장·재접속·본인 조회·공개 중단·저장 해제를 확인했습니다. `npm run check`와 `npm run test:e2e`도 통과했습니다. 로컬 Docker DB 전체 검사는 실행하지 않았습니다. 기능을 내릴 때는 화면을 되돌리고 저장 기록을 보존합니다.

## 운영 요일과 고려대 공개 혜택

`20261126065652_discounts_offer_weekdays.sql`은 선택적으로 ISO 요일(월요일 1, 일요일 7)을 설정합니다. 검색의 **오늘 이용 가능** 필터와 캘린더가 주어진 날짜의 운영 요일을 확인합니다. 입력이 없는 기존 제보는 기존 날짜 기준을 따릅니다.
